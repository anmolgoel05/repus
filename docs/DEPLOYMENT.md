# Deployment

## Local

Install Node.js 22.13 or later and npm 10 or later. Copy `.env.example` to `.env` and configure secrets. For host processes, start PostgreSQL and Redis with `docker compose up -d --wait postgres redis`, then wait for role provisioning to finish with `docker compose run --rm --no-deps db-roles`, install dependencies with `npm ci`, generate the Prisma client with `npm run db:generate`, and apply migrations with `npm run db:migrate`. Start `npm run dev`, `npm run worker`, and `npm run event-worker` in separate terminals. The `db-roles` service reconciles `repus_api` (`NOBYPASSRLS`) and `repus_worker` (`BYPASSRLS`) from `API_DB_PASSWORD` and `WORKER_DB_PASSWORD`. `DATABASE_URL` uses the API role, migration commands use `MIGRATION_DATABASE_URL`, and queue workers use `WORKER_DATABASE_URL`.

On a Docker host, run the complete local stack and check all four runtime services:

```sh
docker compose config --quiet
docker compose up --build --wait --wait-timeout 180
docker compose ps --all
docker compose exec -T api node tools/service-readiness.cjs api
docker compose exec -T web node tools/service-readiness.cjs web
docker compose exec -T worker node tools/run-with-env.cjs --worker-db node tools/service-readiness.cjs worker
docker compose exec -T event-worker node tools/run-with-env.cjs --worker-db node tools/service-readiness.cjs worker
```

Expect `db-roles` and `migrate` to exit successfully and the four runtime services to be healthy. The worker probes check PostgreSQL and Redis connectivity. To verify job processing, run the Playwright journey from the host with the Compose ports and database roles configured in `.env`. This exercises CSV import, campaign scheduling and development delivery through the running services. Record container verification in the implementation checklist after running it on a Docker host.

The API image starts Node directly. The worker images start the environment launcher directly so it selects `WORKER_DATABASE_URL` and forwards Docker's stop signal to the worker. Compose supplies `PUBLIC_MEDIA_URL` to the API and sending worker and gives both workers two minutes to drain. On the deployment host, verify a controlled `docker compose stop worker event-worker` finishes within that grace period, then bring the services back up.

For host processes, use `node tools/run-with-env.cjs node tools/service-readiness.cjs api` and `node tools/run-with-env.cjs node tools/service-readiness.cjs web`. The probes use `PORT` for the API and `WEB_PORT` for the web app, with defaults of 4000 and 3000. Inside Compose the probes use the container ports, regardless of the published web port.

For either worker, run `node tools/run-with-env.cjs --worker-db node tools/service-readiness.cjs worker`. Compose uses the same command so the dependency probe checks the same database connection as the worker process.

Use the same `PLATFORM_TIMEZONE` on the API, email worker and event worker. The event worker uses it to attribute SES acceptance to the same quota day as the sending worker, including when provider events arrive after a day boundary.

The manually dispatched `Verify Repus` workflow includes a `compose-acceptance` job on a disposable Linux runner. It builds the backup image and application stack, waits for Compose health checks, verifies effective Redis durability settings, and runs the Chromium journey. Both workers must exit with code zero after draining. The current Next.js build exits with code 143 after handling SIGTERM. The launcher preserves those explicit child exit codes. The workflow then replaces the Redis container and checks that a short-lived test key survives on the named volume and that the API reconnects. On failure it reports container health, exit status and out-of-memory status before removing the disposable volumes. Encrypted backup and recovery drills and their artifacts stay local. The Compose job still needs its first run.

For release acceptance, record the revision and the result of each Compose step. Use a disposable stack because the workflow deletes its volumes at teardown. Record the AWS acceptance separately with the deployment region, verified sender identity, timestamps and the observed provider event types. Use synthetic contacts and operator-controlled mailboxes. Record whether the application stored each event and whether the corresponding status, quota and suppression changed as expected. Keep session cookies, tokens, credentials, message bodies and backup artifacts out of the record.

### Inbox and tracking acceptance

Send a synthetic campaign through the deployed SES configuration to operator-controlled inboxes. Use a message with a preheader, personalized subject, two-column content, an uploaded image, a tracked link and an unsubscribe footer. Open the received message in actual desktop and mobile clients. Record the client and version, viewport, image loading, column stacking, text alternative, link destination and unsubscribe behavior. Check the delivered message headers for `List-Unsubscribe` and `List-Unsubscribe-Post` without retaining the capability URL.

Record delivery and engagement counters before opening the message, after the first open and click, and after repeating them. Repeat with email privacy protection enabled where available, recording any prefetch or proxy behavior separately from manual interaction. Verify repeated activity for one recipient does not inflate unique counts. Submit unsubscribe using a separate test recipient and verify the next campaign excludes that address. Keep traffic within the approved tracking limit and record any throttled requests separately. This check requires live inboxes and remains pending.

The SES event worker gives each SQS long poll a 30-second abort deadline. Message deletion and visibility renewal use 15-second abort deadlines. Each message has at most one renewal in flight. Shutdown cancels the current long poll and waits for active message processing and its final renewal before closing SQS and database resources. Verify this path with a live SQS queue during deployment acceptance.

### Encrypted PostgreSQL backups

The optional Compose `backups` profile creates an encrypted custom-format dump immediately and once per `POSTGRES_BACKUP_INTERVAL_SECONDS` (default: 24 hours). The dump streams directly through encryption, so a full plaintext archive is not staged on the container filesystem; Bash `pipefail` makes a failure from either PostgreSQL or OpenSSL fail the backup. Generate a high-entropy encryption secret and store it only in `.env` or a secret manager:

```sh
node -p "require('node:crypto').randomBytes(48).toString('base64url')"
```

Set the output as `POSTGRES_BACKUP_ENCRYPTION_KEY`, then run `docker compose --profile backups up -d db-backup`. The backup role is the existing trusted worker role so row-level security does not omit tenant data. Backups are encrypted with AES-256-CBC using PBKDF2, authenticated with a separately derived HMAC-SHA256 key, written mode `0600`, and locally retained for `POSTGRES_BACKUP_RETENTION_DAYS` (default: 30). Key material is never written beside the backup. The local named volume is not an off-host backup; copy encrypted `.dump.enc` and `.hmac` pairs to private off-host storage and keep the encryption key separately.

Run one immediate backup without starting the scheduler with `docker compose --profile backups run --rm db-backup once`. The container logs only the timestamped filename and success/failure; inspect the backup volume to confirm the `.dump.enc` and matching `.hmac` files exist.

To restore, first create a new empty disposable database, then run the restore tool with that database's owner URL and an explicit confirmation. It authenticates the encrypted file before decryption and checks for existing relations, routines, user-defined types, non-default schemas, large objects, and extensions before writing; it does not drop existing objects:

```sh
docker compose exec postgres createdb -U repus restore_test
docker compose --profile backups run --rm -e RESTORE_DATABASE_URL='postgresql://repus:repus_dev_password@postgres:5432/restore_test' -e RESTORE_CONFIRM=RESTORE_TO_EMPTY_DATABASE db-backup /usr/local/bin/postgres-restore /backups/repus-<timestamp>.dump.enc
```

Use the actual timestamped filename from the backup volume. These tools use libpq URLs; do not append Prisma's `schema` parameter. Restores omit ownership and ACLs: reapply `infrastructure/postgres/01-application-roles.sql` with the intended runtime-role passwords and restored database connection before running the API, then verify tenant RLS. Remove the disposable restore database after validating application queries against it. `npm run test:backup` automates a local synthetic-data drill, including restored grants and RLS; recovery verification remains local and is not uploaded to CI. Production operators must automate off-host transfer and retention, protect the encryption key in a separate secret store, and regularly test restores in an isolated database before relying on these local backup tools.

## AWS/VPS production outline

The web production build uses Next.js with Webpack. Run `npm run build` from the repository root to build its dependencies and the application, then use `npm run start -w @repus/web` to serve the built web app.

Use HTTPS origins on the same site for the web app and API, such as `https://app.example.com` and `https://api.example.com`. The browser sends the host-scoped `SameSite=Lax` session cookie to the API on credentialed requests within that site. Set the API's `NEXT_PUBLIC_APP_URL` to the exact web origin for CORS. Set `NEXT_PUBLIC_API_URL` to the public API origin before building the web app, or pass it as the `web` Docker build argument. Next.js embeds it in browser assets, so changing it requires rebuilding the web image. Verify sign-in and an authenticated request through the public web origin after deployment.

1. Configure the domain and DNS, TLS, Cloudflare proxy/WAF, and a public HTTPS tracking subdomain; set `TRACKING_BASE_URL` on the email worker and API to that origin. Set `TRUST_PROXY_HOPS` for the API to the exact number of trusted reverse proxies between clients and Express (1 for a single directly-connected proxy); production startup rejects a missing, zero, malformed, or excessive value so client-IP throttling cannot silently collapse to the proxy address.
2. Deploy web, API, email worker and event worker as separate restartable containers on a 2–4 GB Lightsail instance or equivalent. Expose only HTTPS; keep PostgreSQL and Redis private. All API replicas must share the same Redis service because Nest throttling counters are stored there atomically; do not use isolated per-replica Redis instances.
3. Use managed secrets or IAM instance roles. Configure `EMAIL_PROVIDER=ses` consistently for the API and both workers; the API and email worker fail closed in production unless SES region/configuration set, private S3 bucket, a valid SES sender address, a 32-character session secret, and HTTPS origins for the app, tracking, and media are configured. All three backend services also require PostgreSQL and Redis URLs with non-loopback hosts. Configure SES region, configuration set, verified sender domain, DKIM, SPF, DMARC, SNS/SQS event destination, and request SES production access. Campaign launch requires SES identity verification and Easy DKIM status `verified`. The email worker defaults to one message per second; set `EMAIL_MAX_SEND_RATE_PER_SECOND` no higher than the account's current SES `MaxSendRate`, and start with low warm-up limits.
   Create an SNS topic for SES events and an encrypted SQS queue subscribed to that topic. Keep raw message delivery disabled so the SNS envelope and signature are preserved. Set `AWS_SES_SQS_URL`, `AWS_SES_SNS_TOPIC_ARN`, and `AWS_REGION` for the event worker. Restrict the SNS topic policy to SES publishing from the expected AWS account and verified SES identity; restrict the queue policy to `sns.amazonaws.com` with the exact topic ARN as `aws:SourceArn`. Grant the worker role only `sqs:ReceiveMessage`, `sqs:DeleteMessage`, `sqs:GetQueueAttributes`, and `sqs:ChangeMessageVisibility` on the event queue. Configure a dead-letter queue and redrive policy. The worker verifies the SNS signature, region certificate host, and exact topic before processing; it renews message visibility during long processing and deletes a message only after durable event processing succeeds. On shutdown it aborts the long poll and drains messages already received. Confirm the SNS subscription during provisioning; the worker intentionally never follows a `SubscribeURL` from a message.
   Configure SES event delivery for accepted/delivery, bounce, complaint, rejection and delay events. Repus performs open and click tracking itself; avoid also publishing SES open/click events into the same analytics stream, which would count the same engagement twice.
4. Deploy [private-storage.json](../infrastructure/aws/private-storage.json) using the [AWS setup guide](../infrastructure/aws/README.md), or provide an equivalent private encrypted S3 bucket. Set `AWS_S3_BUCKET` from its bucket-name output. Attach its API policy only to the API role (upload/read/delete and multipart abort) and worker policy only to the sending/import worker (read/delete plus bucket listing for the bounded hourly orphan sweep). The web and event worker need no storage policy. The sweep ignores objects younger than 24 hours and deletes only unregistered image keys. The template blocks public access and ACLs, requires TLS, aborts incomplete multipart uploads after one day, and retains completed objects and the bucket on stack deletion. Do not add age-based image expiration: sent campaigns may still reference them. Complete the live role/anonymous-denial checks in the setup guide before production acceptance. Set `PUBLIC_MEDIA_URL` to the public HTTPS API/media origin; image objects remain private and the API streams them after validating the image capability. Local development uses `IMPORT_STAGING_DIR` for private files; persist this path across restarts.
5. Persist PostgreSQL and Redis data. Schedule encrypted off-host PostgreSQL backups, test restores, monitor queue depth, failed jobs, delivery/bounce/complaint rates, provider quota and event lag in CloudWatch.
6. Configure firewall rules, TLS renewal, health checks, resource limits, log retention, alerts, incident contacts and emergency sending pause.

Before enabling live sending, assign primary and backup abuse-response owners and configure alert routing using [the abuse-response runbook](ABUSE_RESPONSE.md). The worker deletes resolved/rejected reports after 365 days; unresolved reports require weekly review. Ship stdout/stderr from the API and both workers to CloudWatch Logs for Embedded Metric Format extraction, deploy the SES and operations alarms, confirm the SNS subscription, and run a controlled alert test. Application alert delivery and escalation routing remain unverified until these deployment steps are complete.

The checked-in Compose file is for local development and does not replace a hardened production deployment. Its API readiness probe checks PostgreSQL and Redis, worker probes check both dependencies, and the web container waits for API readiness. The API also keeps a separate liveness endpoint. Review every table's RLS policy and runtime grant before production use; the API role is non-owner and cannot bypass RLS, while only trusted queue workers can bypass it. Runtime containers receive service-specific environment values and do not inherit the shared `.env` file wholesale. Rotate development passwords and supply managed production credentials. SES sandbox status and quotas are account/region specific and must be confirmed before enabling live campaigns.

Redis queue durability requires persistent storage and AOF; Compose enables AOF and mounts `redis_data`. The local `npm run test:redis-recovery` drill passed an isolated Redis crash/restart after an explicit `WAITAOF` durability point, including preserved waiting/delayed jobs and actual worker recovery without duplicate provider acceptance or quota consumption. This verifies acknowledged AOF persistence, not zero loss of writes that have not yet been fsynced. PostgreSQL remains the authoritative campaign/recipient ledger: workers republish eligible queued recipients, and uncertain provider outcomes remain reserved for reconciliation rather than automatic resend. Verify storage persistence, Redis eviction policy, failover and restore behavior on the actual production host before launch.

SES requests have a 30-second client timeout. A timeout, shutdown interrupt, or ambiguous provider error can leave a recipient in `SENDING` while Repus waits for an authenticated SES event to resolve whether the message was accepted. These outcomes retain quota and are never automatically retried, because retrying an accepted message could duplicate it. Campaign results show a warning after 15 minutes; operators should resolve stale cases against SES records. Platform admins can review and resolve these cases in the admin dashboard with an audited evidence note; see the [API guide](API.md) for the route and payload.
## Platform operations access

Account emails require the sending worker and the verified platform `EMAIL_FROM_ADDRESS`, including while marketing is paused. The API records an encrypted outbox; it no longer calls SES for verification/reset/invitation requests. Pending rows are reconciled every 15 seconds and queue payloads contain only token IDs. Account jobs precede subscriber confirmations, test emails and marketing jobs, within the same provider rate limit. Configure SES capacity for transactional mail as well as marketing volume.

For account-delivery triage, a trusted operator can inspect aggregate counts with `SELECT purpose, delivery_status, count(*) FROM one_time_tokens WHERE created_at > NOW() - INTERVAL '7 days' AND (token_encrypted IS NOT NULL OR delivery_status <> 'PENDING') GROUP BY purpose, delivery_status;`. `FAILED` jobs require configuration/provider review and a fresh recovery or invitation request. `SENDING`/`UNCERTAIN` may already have reached SES; authenticated notices can reconcile acceptance, and the user can request a new link. Keep those outcomes unretried rather than resetting their database claim. Terminal queue failures remain visible to the existing queue-health alarms. SDK write retries are explicitly disabled, including when `AWS_MAX_ATTEMPTS` is set externally; application logic controls safe retries.

Run local backup and worker-recovery drills sequentially when they share a PostgreSQL cluster: both bootstrap the same global development roles. Recovery verification and its artifacts remain local.

Apply migration `202611040001_import_staging_cleanup` before starting the updated CSV worker. The worker retries deletion of completed and cancelled import files and records successful cleanup in PostgreSQL. Failed imports retain the source file for retry. PostgreSQL recovery preserves the cleanup records. Include the private object store in the deployment recovery plan for files needed by pending or retryable imports.

When upgrading through `202611030002_acceptance_event_history`, drain and stop the API and both workers, apply migrations, then start the new builds together. This lets the previous acceptance writers finish before the backfill and activates the transactional writer consistently. The migration fills missing history without replacing existing accepted events; local recovery verification exercises it twice against missing and existing history before backing up and restoring the result.

The admin dashboard includes persisted daily/monthly defaults for new workspaces. The additive `202611030001_default_tenant_quotas` migration leaves both values null so existing environment defaults continue to apply. Changes affect only subsequent workspace creation; use the tenant controls for deliberate changes to an existing tenant. All changes are audited. Reset a default to null to resume its environment fallback.

Set `PLATFORM_ADMIN_EMAILS` to a comma-separated allowlist of verified operator email addresses in the deployment secret store. Platform operators sign in with normal accounts; workspace API keys never receive this access. The dashboard can pause/suspend workspaces and change tenant quotas. Changes are audited. Configure the allowlist narrowly, and protect the deployment environment as a production secret.

The audited global sending pause prevents new campaign reservations and publishes a Redis interrupt to active campaign and test-email senders. Worker processes pass an AbortSignal to the SES SDK; because SES may already have accepted a request when it is interrupted, Repus keeps that recipient in SENDING for authenticated event or operator reconciliation and never retries it automatically. Monitor uncertain sends until they are reconciled.

Platform daily and monthly send limits can be set in Platform admin. A blank limit uses the corresponding `PLATFORM_DAILY_SEND_LIMIT` or `PLATFORM_MONTHLY_SEND_LIMIT` environment value (defaults 2500 and 75000). A value of zero disables new campaign reservations for that period. Changes are persisted and audited.

Verify `EMAIL_FROM_ADDRESS` in SES before enabling double opt-in in production. Confirmation messages use the configured Repus sender identity and run through the durable email worker queue; they are not sent from an unverified tenant address.

### Resolving uncertain SES outcomes

Campaign reports identify recipients left in `SENDING` for more than 15 minutes. Platform admins can review these in the Repus admin dashboard. Before resolving one, check SES account/message evidence. Confirm acceptance only with the SES message ID; confirm non-acceptance only when provider history supports that conclusion. Both decisions require an audit note and are recorded in the platform audit log. A later authenticated provider event remains authoritative and can correct an earlier non-acceptance decision.

AWS event infrastructure is provisioned with the CloudFormation stack in [infrastructure/aws](../infrastructure/aws/README.md). The stack provides the SES configuration set, Easy DKIM identity, encrypted SNS/SQS path, dead-letter queue, queue policies, and worker IAM permissions scoped to explicit SES identity ARNs. Tenant identities must be provisioned by an operator and added to that ARN list; DNS publication, SES production access, SPF/DMARC, and production smoke verification remain operator steps.
