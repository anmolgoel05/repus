# Database

Every Prisma PostgreSQL pool pins its session timezone to UTC, including when a connection URL requests another timezone. Prisma's pg adapter serializes DateTime parameters without an offset; leaving a server-local session timezone would shift TIMESTAMPTZ writes and due-date filters. Workspace/platform timezone calculations remain explicit in application logic and analytics SQL. PostgreSQL regressions verify the session setting, exact stored instants and inclusive/exclusive scheduled-date comparisons.

PostgreSQL 15+ is the durable source of truth. Prisma schema changes must be accompanied by committed migrations (`npm run db:migrate`); do not use schema push/synchronization in deployed environments.

The `202610310002_organization_memberships` migration creates and backfills `organization_memberships` from existing user tenant/role/status values, adds tenant-scoped membership RLS, and adds `tenant_id` to one-time tokens. It replaces the legacy session-to-home-tenant foreign key with separate user/tenant references plus a composite session-to-membership constraint, allowing a session to switch only to a workspace where its user has membership. Session resolution checks that membership is active before installing the tenant claim; API authorization resolves the role from that membership. The dashboard can discover, create, and switch workspaces, and invitations can add existing Repus accounts without changing their home tenant. Apply the migration before deploying the new API, then run the database RLS and browser journey checks with a non-owner API database role.

Tenant-owned tables include `tenant_id`, use composite tenant-aware references, and are protected by RLS with the transaction-local `app.tenant_id` session variable. API transactions must set it before tenant queries. API key lookup has a narrow `app.api_key_hash` policy to resolve the key's tenant; the request then enters that tenant's normal RLS transaction. Account bootstrap uses `withAuthUserEmail`, `withSessionToken`, and `withOneTimeToken` to resolve a tenant from a normalized email or one-time hash before regular tenant-scoped reads. Platform quota controls add tenant and `app.platform_admin` policies to `tenant_sending_limits`; allowlisted operators must use `withPlatformAdmin`, which writes platform audit records in the same transaction. Email addresses are normalized before uniqueness checks. Unsubscribe/suppression history is append-only.

`tenant_sending_limits.media_storage_limit_bytes` stores the per-workspace private image storage cap (100 MiB by default). `quota_overrides` records which send, contact, and media limits were explicitly set by a platform operator, so future subscription entitlement synchronization can preserve those decisions. Uploads serialize quota checks by tenant under a PostgreSQL advisory transaction lock, so concurrent uploads cannot exceed the configured cap.

The image orphan sweeper uses `withTrustedWorker` to perform a read-only lookup of candidate object keys under a dedicated `image_assets` SELECT policy. It deletes a stale storage object only when that lookup confirms no capability record exists.

`campaign_recipients.provider_accepted_at` is an idempotency marker for quota settlement. The send worker records acceptance from the SES response; the event worker can do the same from authenticated SES events when the send process exits before persisting the response. A global quota advisory lock and the marker prevent duplicate acceptance events from incrementing sent usage twice. Each recipient also stores `quota_date`: active reservations roll into the current platform-local date immediately before provider submission, and a provider acceptance timestamp crossing midnight transfers the reservation to the actual acceptance date.

`send_started_at` timestamps the provider-boundary attempt. Campaign stats use it to surface `SENDING` rows older than 15 minutes without an acceptance marker; those rows retain their quota reservation until reconciliation.

`platform_daily_usage` is intentionally global and has no `tenant_id`; its RLS policy permits access only within a tenant, platform-admin, or trusted-worker transaction. Campaign reservations, provider acceptance, terminal failure, cancellation, and delayed-schedule quota rebasing update this ledger and tenant `daily_usage` under the same PostgreSQL advisory lock. A due scheduled campaign is capacity-checked and its recipient rows are changed to `QUEUED` in the same transaction that moves reservations to the current platform day. If an active campaign reaches its next local day after an outage, each remaining recipient is independently checked and rebased; quota-blocked BullMQ jobs are durably delayed until the next local midnight. The API uses the global ledger for platform daily/monthly checks; it must not infer platform totals by aggregating RLS-filtered tenant rows.

Deployments must separate credentials by service. Run migrations as the schema owner. Run the API as a non-owner role subject to RLS, and run both queue workers with the dedicated trusted internal `BYPASSRLS` role that can read/write cross-tenant campaign and delivery data. Grant runtime roles only required schema/table/sequence privileges; never run production services as the migration owner. Host-launched API development uses `DATABASE_URL`; migration commands use `MIGRATION_DATABASE_URL`; worker launch commands select `WORKER_DATABASE_URL`. Local Compose reconciles roles before migrations. To exercise policy enforcement, apply migrations using the owner URL, set `RLS_TEST_DATABASE_URL` to the `repus_api` URL, then run `npm run test --workspace @repus/database`. `TEST_DATABASE_URL` is used by worker integration tests and by older tenant-isolation test configurations; avoid pointing it at the owner if you need RLS enforcement. The local Compose credentials are development-only.

The schema covers users, sessions, verification/reset tokens, tenant plan metadata, active organization memberships, tenant-owned hashed API keys, contacts/lists, tenant-owned custom-field definitions, templates/campaigns/recipients, suppressions, quotas/usage, domains, events, imports (including tenant-scoped row errors and resumable batch progress), tenant/platform audit records, and provider-neutral billing subscription snapshots. Every one-time auth or invitation capability has a tenant ID; migration backfills legacy account tokens before making that scope mandatory. Billing rows store provider/customer/subscription references, plan/status, billing period, and cancellation-at-period-end state under tenant RLS; checkout and provider webhook lifecycle are not implemented yet. Custom-field definitions constrain stable JSONB keys; archived definitions preserve their contact values. Deleted contact profiles are anonymized and timestamped; campaign recipient/event snapshots remain available for reporting. Event reporting indexes cover tenant/type/time queries and unique engagement rows. Time values use UTC `TIMESTAMPTZ`; event partitioning can be introduced when volume justifies it.

`abuse_reports` intentionally has no tenant identifier. Anonymous intake runs inside `withPublicAbuseReport`, whose transaction-local claim permits inserts only; public report creation uses `createMany` so it does not need permission to read rows back. Only the allowlisted platform-admin RLS claim can select or change reports. Status updates and report IDs are included in the platform audit log.

`platform_queue_health_samples` stores only aggregate queue names, status, and counts. Trusted workers may insert and prune samples; allowlisted platform admins may read them inside `withPlatformAdmin`. The worker retains 30 days of history for the operations dashboard.

Double opt-in is controlled by `tenants.double_opt_in_enabled`. Contact confirmation tokens carry a tenant/contact composite foreign key and a one-time hash capability. Public token resolution sets `app.contact_confirmation_token_hash` and then installs the resolved tenant claim; anonymous callers cannot enumerate tokens. The encrypted raw token and queue retry metadata let the delivery worker recover confirmation messages after a process restart.
