# API

Campaign schedule and reschedule requests require `scheduledAt` as an ISO timestamp with a timezone, such as `2026-11-10T12:00:00Z` or `2026-11-10T17:30:00+05:30`. Date-only values and timestamps without an offset return HTTP 400.

`POST /api/v1/campaigns/:id/test` returns `{ "data": { "queued": true } }` after the test job is acknowledged by the queue. Delivery happens asynchronously. If publication cannot be confirmed, the endpoint returns HTTP 503 with `SERVICE_UNAVAILABLE`. If the queue accepted the job before the acknowledgment was lost, the test email may still arrive. Check the recipient’s inbox before repeating an unconfirmed request.

Use `GET /api/v1/campaigns?view=summary&page=1` to browse campaigns without message bodies or editor state. The response contains `data`, `page`, and `hasNext`. Pages contain up to 25 campaigns in descending creation order, with campaign ID breaking ties. `view=summary` without `page` returns the unpaged summary array under `data`. The default list response retains the full campaign fields.

Campaign statistics include `lastReputationPause` with a normalized reason and timestamp when the campaign has an automatic pause in its audit history. This entry describes the last automatic pause and can still appear after the campaign resumes.

The campaign recipients endpoint returns `failureType` for recipients currently marked `FAILED` when their event history contains a provider rejection or rendering failure. It returns the normalized event type or `null`. The response omits raw provider error details.

Campaign statistics and workspace overview rates use a single PostgreSQL snapshot for acceptance, recipient outcomes and engagement totals. Both count each accepted recipient once per delivery, bounce, or complaint outcome. The daily series counts each recipient once per outcome per workspace-local event day. The campaign event history retains individual notices and supports `GET /api/v1/campaigns/:id/events?type=rendering_failure`.

Account verification, password-reset and invitation operations persist an encrypted delivery outbox before returning. Production responses do not expose the capability; the worker submits the email after commit. Verification/reset/invitation development URLs remain available only in development. Delivery failure cannot turn password recovery into a provider-dependent account-existence response because SES submission happens in the worker.

Platform admins can set new-workspace daily/monthly quotas through `PATCH /api/v1/admin/settings` using `defaultTenantDailyLimit` and `defaultTenantMonthlyLimit`. Values are nonnegative integers (daily maximum 10,000,000; monthly maximum 100,000,000). `null` resets a field to its corresponding `DEFAULT_TENANT_*` environment value. Zero is an explicit zero allowance. Settings responses include effective values in `tenantDefaults: { dailyLimit, monthlyLimit }`. Changes are audited and apply only to subsequently created workspaces, including registration; existing tenant limits and overrides are unchanged.

`GET /api/v1/analytics/overview` includes lifetime provider-accepted sends as `accepted`, campaign-recipient unique counts as `uniqueOpens`/`uniqueClicks`, their rates, total engagement events, and `contactGrowth: [{ date, added }]` for the last 14 workspace-local calendar days. Contact growth counts contacts created during each day, excludes deleted and future-dated contacts, and fills missing days with zero. It measures contacts added, rather than reconstructing historical active-subscription totals. All aggregates use authenticated tenant scope and RLS.

Versioned API base: `/api/v1`. Swagger UI is served at `/api/docs` in development.

Campaign, list, and template PATCH requests accept partial editable fields through runtime-validated DTOs. Unknown fields, including tenant IDs and campaign status/quota fields, are rejected; non-empty resource names must contain a non-whitespace character. Campaign updates also use an explicit persistence allowlist.

Campaign create/update bodies may include versioned `editorJson`, normalized with the same block, formatting, and background validation as reusable templates. The detail read returns this state for reopening drafts in the visual composer; legacy HTML drafts remain supported. An optional `replyTo: null` clears a saved reply-to address.

Provider bounces/complaints and public unsubscribe capabilities apply to the original campaign-recipient email snapshot. After a consent-backed contact address change, late events or an old unsubscribe link suppress the original address without changing the replacement address's subscription; historical unsubscribe records remain available.

Public unsubscribe uses a case-insensitive address match within that tenant to suppress queued recipients across campaigns and publish interrupts for every matching in-flight recipient ID. A provider may already have accepted an in-flight request; those uncertain outcomes remain reserved for reconciliation.

`GET /api/v1/billing/overview` returns the authenticated workspace's latest subscription status and tenant-scoped daily, monthly, contact, and image-storage usage. Without a provider subscription, it returns the stored workspace plan with status `free` or `managed` and no provider reference. Send windows follow the configured platform timezone, matching quota enforcement. It never exposes payment-provider customer or subscription identifiers. `billingEnabled` remains false until optional provider checkout and signed webhook integration are configured. Displayed limits come from the same tenant quota controls enforced by campaign sends, contact creation, and media uploads.

`GET /api/v1/analytics/overview` returns tenant-scoped totals, up to five recent campaigns, up to eight recent delivery/engagement events (without recipient email addresses), and a tenant-timezone daily series for the last 14 days. Delivery, bounce, complaint, unique-open, and unique-click rates use provider-accepted messages as their denominator; they are `null` before any accepted sends. Daily send counts and event counts are aggregated in PostgreSQL. `GET /api/v1/analytics/daily` returns that same workspace-local series using only the two bounded daily aggregate queries.

Response errors use HTTP status plus `{ statusCode, code, message, requestId }`; internal exceptions are not returned. Authenticated routes use server-side sessions and tenant scope from the session. DTOs validate bodies, and UUID-backed resource paths reject malformed IDs before database access. API rate limits use atomic shared Redis storage so limits apply across replicas; registration and login are limited to five requests per minute, and password-reset requests to three. Public unsubscribe/tracking and signed provider webhooks are narrowly rate-limited and do not expose tenant data.

`POST /api/v1/auth/refresh` rotates the current HTTP-only session cookie and extends its seven-day expiry. Session tokens are single-use: the previous cookie stops working after rotation. The dashboard refreshes on entry and every six hours while open; expired sessions, disabled users, and API keys cannot be refreshed.

`PATCH /api/v1/auth/profile` accepts `{ "name": "Avery Morgan" }` and updates the signed-in user's display name across workspaces. The API accepts 2–120 non-whitespace characters after trimming, records an account-profile audit entry in the currently selected workspace, and never accepts a user or tenant ID from the client.

`GET /api/v1/organizations` lists the signed-in user's active workspace memberships. `POST /api/v1/organizations` creates a workspace with default sending limits and an owner membership; the current session must then switch to the new workspace. `POST /api/v1/auth/switch-workspace` accepts `{ "tenantId": "<uuid>" }`, verifies active membership, rotates the session token, and updates its workspace atomically. Roles are resolved from the active workspace membership, and the database requires every session's `(tenant_id, user_id)` pair to exist in `organization_memberships`.

Owners and admins can manage memberships through `GET /api/v1/organizations/members`, `POST /api/v1/organizations/invite`, `POST /api/v1/organizations/members/:id/invitation`, `POST /api/v1/organizations/members/:id/restore`, `PATCH /api/v1/organizations/members/:id/role`, and `DELETE /api/v1/organizations/members/:id`. `POST /api/v1/organizations/invitations/accept` consumes the emailed invitation once. Existing active Repus accounts keep their password and home workspace; new or still-pending accounts choose a password while accepting. Revoking a membership removes sessions and API keys scoped to that workspace without deleting the account or its other memberships.

Authentication responses, including verification and password-reset requests, use `no-store` cache headers. The verification and reset pages also set `Referrer-Policy: no-referrer` and `nosniff`; token errors receive the same API response headers.

`POST /api/v1/auth/verification/resend` accepts `{ "email": "..." }`, is limited to three requests per minute, and returns generic success for unknown, active, and pending accounts. For pending accounts it invalidates prior unused verification tokens, creates a fresh 24-hour capability, and sends a new link; development responses include the local verification URL.

`POST /api/v1/auth/password-reset/request` also returns generic success in every environment. In development it includes a browser-only reset URL for local testing; unknown addresses receive an unusable random link with the same response shape. Development email logs omit recipient addresses and raw capability URLs.

Custom-field definitions support `GET/POST /api/v1/custom-fields`, `PATCH /api/v1/custom-fields/:id`, and `PATCH /api/v1/custom-fields/:id/archive` with `{ "archived": true|false }`. Definitions have tenant-scoped keys and TEXT/NUMBER/DATE/BOOLEAN types. Archived definitions and contact values are retained and can be restored. Owners/admins can manage definitions; manual create/edit values and CSV imports validate active definitions and their required/type constraints. Import column mappings may include definition keys, and full/selected CSV exports include values for defined keys.

Manual subscriber creation with `POST /api/v1/contacts` requires documented permission evidence. `consentSource` is trimmed, limited to 240 characters, and must contain non-whitespace text; `consentAt` must be a strict ISO date/time no later than the current time. The API returns HTTP 409 if the normalized address is suppressed in the active workspace, even after deletion of the original contact. If an unsubscribed contact still exists and has given fresh permission, use the reactivation endpoint below.

Full contact exports, selected-contact exports, and import error reports return attachment responses marked `private, no-store` with `nosniff`, because they can contain addresses, permission metadata, and uploaded row values.

Unsubscribe and double-opt-in confirmation capability pages and responses, tracking pixels, and click redirects use no-store caching, `Referrer-Policy: no-referrer`, and `X-Content-Type-Options: nosniff` to keep capability URLs from being cached or forwarded as referrers.

Contact profiles are available at `GET /api/v1/contacts/:id` and can be edited with `PATCH /api/v1/contacts/:id`. The detail response includes tenant definitions, permission metadata, and timestamped unsubscribe history; the UI provides profile/custom-field editing plus archived-value visibility. Changing a contact's email requires an explicit fresh-permission attestation and source/date, for example `{ "email": "new@example.com", "consentConfirmed": true, "consentSource": "Website signup form", "consentAt": "2026-01-15" }`. The destination is checked against workspace suppressions and contacts under the tenant lock. Queued campaign recipients still holding the old address are suppressed and their quota reservations released; active provider calls receive a recipient-scoped interrupt. A successful change replaces the prior consent record; when double opt-in is enabled, previous unused confirmation links expire and the response includes `confirmationRequired: true` while the new address awaits confirmation. Without fresh evidence, the request is rejected.

An unsubscribed contact can only be reactivated with `POST /api/v1/contacts/:id/reactivate` and `{ "consentConfirmed": true, "consentSource": "New website signup", "consentAt": "2026-10-31" }`. The tenant lock protects this transition, and the API records an audit entry. It clears only an unsubscribe suppression; hard-bounce and complaint suppressions remain. If double opt-in is enabled, the unsubscribe suppression remains until the subscriber completes the fresh confirmation link. Importing the address alone never reactivates it, and unsubscribe history is retained.

`GET /unsubscribe/:token` displays the confirmation page without changing subscription state. `POST /unsubscribe/:token` accepts the confirmation form or a mailbox client's URL-encoded `List-Unsubscribe=One-Click` request. The token authorizes the request without a session cookie. The POST immediately suppresses the address in the sender's workspace and returns an HTML confirmation. Replaying the same recipient token does not append a duplicate unsubscribe event or history row. Contact deletion preserves those records and the suppression.

Owners/admins can manage bearer API keys with `GET/POST /api/v1/api-keys` and revoke with `DELETE /api/v1/api-keys/:id`. Creation accepts `{ "name": "nightly sync", "role": "VIEWER", "expiresAt": "2030-01-01T00:00:00.000Z" }`; `expiresAt` is optional and roles are limited to `VIEWER` or `MARKETER`. A `VIEWER` key is read-only. The raw `rps_live_...` key is returned once. Send it as `Authorization: Bearer <key>`; metadata endpoints never return the hash or secret. Key requests use the tenant and restricted role bound to that key.

Workspace access can be revoked with `DELETE /api/v1/organizations/members/:id`. This disables only the selected workspace membership, removes its sessions, invalidates its pending invitation tokens, revokes keys the member created in that workspace, and retains the account and audit history. Owners can revoke admins; admins can revoke non-admin members. The owner and the current actor cannot be removed through this endpoint. Role edits and removals atomically require the target role/status to still match the authorization read; if another action changes either, the API returns HTTP 409 before audit or revocation side effects. Refresh the member list before retrying.

Pending or revoked memberships can receive a fresh seven-day invitation with `POST /api/v1/organizations/members/:id/invitation`. It sets the membership to pending and invalidates older unused invitations only for the selected workspace. Links for the same account in other workspaces stay valid. Only owners can resend an admin invitation. Development returns the invitation link for local testing. Previously verified members can be restored with `POST /api/v1/organizations/members/:id/restore`; this restores ACTIVE status but does not recreate sessions or previously revoked API keys. Both operations return HTTP 409 if the role or membership status changes before the write; a failed resend rolls back token changes.

Reusable templates use `GET/POST /api/v1/templates` and `GET/PATCH/DELETE /api/v1/templates/:id`. Composer-created templates include an optional versioned `editorJson` document (`{ "version": 1, "blocks": [...] }`) for restoring supported heading, paragraph, button, image, columns, and divider blocks. The API validates the block count, kinds, and field sizes; email HTML is sanitized independently before persistence. Templates created before block layouts were saved can still be loaded as a plain-text paragraph in the composer.

Workspace editors can upload PNG, JPEG, or WebP files up to 5 MB with `POST /api/v1/media/images` as multipart field `file`. Images are stored in private S3 (or the private local development staging directory), scoped to the authenticated tenant, and served to email clients through a random capability URL at `GET /media/assets/:token`. `GET /api/v1/media/images` lists the current tenant's library; `DELETE /api/v1/media/images/:id` removes an image only when no saved campaign or template refers to it. Configure `PUBLIC_MEDIA_URL` to the externally reachable HTTPS origin for the API/media service in production. SVG and MIME-only file disguises are rejected.

Workspace owners/admins can enable double opt-in in organization settings (`PATCH /api/v1/organizations/current` with `{ "doubleOptInEnabled": true }`). New manual contacts and CSV imports remain `PENDING_CONFIRMATION`; a one-time email capability expires after 48 hours and a separate POST confirmation activates the contact. Link scanners and previews that only issue GET requests do not subscribe the contact. Workspace members with write access can use `POST /api/v1/contacts/:id/confirmation/resend` (five requests per hour per client) for a pending contact; the action expires earlier outstanding links, creates a fresh 48-hour token, and is audited. The workspace setting is off by default; existing contacts retain their current state. Definite send failures advance through bounded retries, while an ambiguous provider outcome is not retried because the confirmation email may already have been accepted. In development, the confirmation link is logged for local testing.

Implemented route groups: `/auth`, `/organizations`, `/contacts`, `/contacts/tags`, `/contacts/export`, `/contacts/import`, `/lists` (`GET /lists/:id` returns a tenant-scoped list with its membership count), `/campaigns` (`POST /campaigns/:id/preview` renders sample subject and body personalization without sending; test sends use the same shared subject/body renderer), `/templates`, `/domains` (`GET /domains/:id` is tenant-scoped), `/analytics` (`GET /analytics/daily` returns the workspace-local 14-day series), and `/admin`. `GET /organizations` lists all active memberships for the authenticated user; `GET /organizations/current` returns the workspace selected by the current session. `POST /organizations` creates a workspace and owner membership, and `POST /auth/switch-workspace` rotates the session while selecting another active membership. Organization routes also include `GET /organizations/members`, `POST /organizations/invite`, `POST /organizations/members/:id/invitation`, `POST /organizations/members/:id/restore`, `PATCH /organizations/members/:id/role`, `DELETE /organizations/members/:id`, and public `POST /organizations/invitations/accept`. Existing active Repus accounts retain their password and home workspace when accepting an invitation; new or pending accounts choose a password. Only owners can grant admin role. In development, invitation URLs are returned only in the local response; production requires SES. Contact list and export endpoints accept `q` and `tag` filters. `POST /contacts/bulk` supports add/remove list membership, add/remove tags, unsubscribe, and anonymizing deletion for up to 500 tenant-owned contacts; `POST /contacts/bulk/export` streams a selected-contact CSV. Deletion removes the contact from the audience, redacts profile and consent fields, suppresses queued sends, and preserves campaign recipient/event history. Campaign reporting endpoints are `GET /campaigns/:id/stats`, `GET /campaigns/:id/events?page=1&pageSize=25&type=open`, and `GET /campaigns/:id/recipients?page=1&pageSize=25&status=DELIVERED&q=alice`; each derives the tenant from the session and returns paginated, privacy-limited results. `POST /contacts/import` accepts a multipart CSV up to 25 MB, previews its headers/first rows, and stages it privately. `POST /contacts/import/:id/start` requires column mapping, an explicit permission attestation, and either a mapped per-subscriber permission date or a shared collection date; status, retry, cancel, import history and rejected-row CSV are also available. Public tracking endpoints are `GET /t/open/:token` (1x1 cache-disabled GIF) and `GET /t/click/:token` (authenticated-capability, campaign-link-validated redirect). Public open/click routes share a 60-request-per-minute-per-client throttle. Campaign actions include `POST /campaigns/:id/pause` for active queued/sending campaigns, `POST /campaigns/:id/resume` to restore queued recipient jobs, and `POST /campaigns/:id/cancel` to cancel scheduled, queued, or paused campaigns. Cancellation conditionally claims a still-cancellable state, suppresses queued recipients, releases their tenant and platform reservations by the returned quota date, and publishes a worker interrupt; an already submitted SES request may still be accepted and is not retried until reconciled. Pause also publishes a worker interrupt with the same uncertain-provider-outcome behavior. Platform operators listed in `PLATFORM_ADMIN_EMAILS` can use `GET /admin/overview` and `PATCH /admin/tenants/:id`; tenant status and quota changes run in an explicit elevated RLS transaction and are recorded in the platform audit log. Paused/suspended tenants cannot launch campaigns. Queued recipients not yet submitted to the provider are suppressed and release their reserved quota. Tenant suspension or disabling sending publishes a tenant-scoped interrupt to active SES requests; SES may already have accepted a request, so that recipient remains uncertain and is not retried. Scheduled campaigns wait until the tenant is active. The event worker accepts production SES events only from a configured private SQS queue and verifies the SNS signature, region, and topic ARN before durable processing; automated AWS resource setup and infrastructure verification remain pending.

When a scheduled campaign reaches launch after its reserved quota date, the worker serializes the launch with other quota changes, checks current daily/monthly tenant and platform capacity, moves the reservation to the current platform day if needed, then changes the campaign and recipient states to queued in the same transaction. If current capacity is unavailable, the campaign remains scheduled and the scheduler retries in a later minute. Malformed quota environment limits fail closed instead of disabling quota comparisons.

Campaign audience validation counts eligible, consented list members in PostgreSQL and excludes suppressions with an anti-join. Recipient rows are inserted from that same database-side selection and the inserted count must match the quota reservation. API and worker queue publishers page queued recipient IDs in batches of 500 using a campaign/status/ID index; a single-flight scheduler recovery scan advances through ten batches per tick and resumes from its last page after transient errors. Scheduled preparation does not materialize the recipient ID set in application memory.

In SES mode, a verified SES sending identity is not sufficient by itself to launch a marketing campaign: Easy DKIM must also report verified. The development adapter accepts its simulated domain status and does not require live DNS records. The send worker retries explicit SES throttling responses with queue backoff, marks permanent provider rejections failed and releases their reservation, and leaves ambiguous provider outcomes in `SENDING` for reconciliation rather than risking duplicate delivery.

Scheduled campaigns retain the eligible recipient snapshot and quota reservation created when scheduling. Their audience list cannot be edited afterward; cancel the schedule and create a new campaign to target a different audience. `POST /api/v1/campaigns/:id/reschedule` changes a future scheduled time and atomically rebases daily/monthly tenant and platform reservations under the quota lock. It rejects capacity overflow or inconsistent recipient reservations without changing the existing schedule.

Platform operators can use `GET /api/v1/admin/health` for live database connectivity, SES account/sandbox/quota status, BullMQ queue depth and failed jobs, and pending/failed provider-event lag. `GET /api/v1/admin/health/history` returns the latest 100 aggregate worker queue snapshots; the trusted worker records them every minute in production and removes records older than 30 days. History is available only to platform administrators, contains no tenant data, and is shown in the admin health panel. The provider response includes `sandbox` (`true`, `false`, or `null` when unavailable), and the admin dashboard displays a prominent warning when SES confirms sandbox access. Database, Redis queues, SES, and event processing report independently so a partial outage remains visible.

`GET /api/v1/health` is a process liveness response. `GET /api/v1/health/ready` performs bounded PostgreSQL and Redis checks and returns HTTP 503 with dependency statuses when either is unavailable; errors and connection details are not returned.

The event worker automatically pauses an active campaign when permanent bounces or complaints meet configured reputation thresholds. `REPUS_REPUTATION_MINIMUM_SAMPLE` defaults to 20 accepted recipients, `REPUS_MAX_BOUNCE_RATE` defaults to 0.05, and `REPUS_MAX_COMPLAINT_RATE` defaults to 0.001. A tenant audit record captures the measured rates and threshold that triggered the pause; an owner/admin can review and resume the campaign after investigating.

Platform operators can read and update global sending controls with `GET/PATCH /api/v1/admin/settings`. Updates accept any combination of `sendingPaused`, `dailySendLimit`, and `monthlySendLimit`. Send limits are non-negative integers; sending `null` clears a saved limit and falls back to `PLATFORM_DAILY_SEND_LIMIT` / `PLATFORM_MONTHLY_SEND_LIMIT` (defaults 2500 / 75000). The response includes the saved values and effective limits. Updates are audited. A pause blocks campaign reservations and new provider submissions across tenants, then publishes an interrupt signal to active campaign and test-email workers. Workers abort matching SES calls where possible; interrupted requests remain uncertain and are not retried because SES may already have accepted them. The pause response reports whether at least one sending worker subscribed to the Redis interrupt, not whether SES stopped processing the request.

`GET /api/v1/media/images` returns `{ assets, usage: { usedBytes, limitBytes } }`. Each workspace has a 100 MiB default image-storage cap, adjustable by platform administrators through `PATCH /api/v1/admin/tenants/:id` with `mediaStorageLimitBytes` (0 to 2,000,000,000). Upload attempts beyond the cap are rejected; concurrent uploads are serialized. Individual images remain capped at 5 MiB.

Anyone can submit an abuse report with `POST /api/v1/abuse-reports`, including the sender email, optional campaign/subject and message ID, a category, and a description. Contact email is optional. The endpoint is rate limited and stores reports behind a narrow insert-only RLS capability. Platform admins can page through reports with `GET /api/v1/admin/abuse-reports?page=1&pageSize=25&status=active`; `active` (the default) orders open and in-review reports oldest first, while `all`, `resolved`, and `rejected` provide other views. Status can be updated with `PATCH /api/v1/admin/abuse-reports/:id` using `in_review`, `resolved`, or `rejected`; status changes are audited.

Subscription confirmation links use `GET /api/v1/confirm-subscription/:token` to show a confirmation screen and `POST` on the same path to activate the pending subscriber. Tokens are random, stored hashed and encrypted, tenant-scoped through RLS, single-use, and expire after 48 hours.

Campaign stats include `uncertainSends`, the count of recipients left in `SENDING` for more than 15 minutes without a provider-acceptance marker. These sends are not automatically retried; quota remains reserved while authenticated SES events can reconcile them. The campaign results view prompts the user to contact Repus support before attempting a manual resend.

Platform admins can review sends that remain `SENDING` for more than 15 minutes with `GET /api/v1/admin/uncertain-sends?page=1` (100 rows per page). Resolve a recipient using `PATCH /api/v1/admin/uncertain-sends/:id` with `{ "outcome": "accepted", "messageId": "ses-message-id", "evidence": "SES message history confirms acceptance" }` or `{ "outcome": "not_accepted", "evidence": "SES account event history confirms no accepted message" }`. Evidence notes are required and decisions are audited. Acceptance records usage exactly once; confirmed non-acceptance releases the quota reservation. A later authenticated SES event can correct a mistaken non-acceptance decision.
