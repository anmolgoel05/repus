# Security and compliance

- Encrypted capabilities accept only canonical, unpadded Base64URL encoding. AES-GCM authentication rejects altered ciphertext; canonical decoding also rejects aliases formed from ignored padding bits or unexpected characters. Tests mutate actual ciphertext bytes and separately exercise alternate encodings.

- Web responses set `Referrer-Policy: no-referrer`, `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, and CSP restrictions for framing, base URLs and object embedding. Verification, password-reset, invitation, subscription-confirmation and dashboard pages disable caching. All `/api/v1` responses use no-store/no-cache protections, including authenticated tenant reads through session cookies or API keys; private downloads retain their stricter download policy. Public capability image responses keep their explicit media caching policy. Live Playwright checks verify actual web headers and authenticated API responses.

- Hash passwords with Argon2id. Use revocable server-side sessions and HTTP-only, Secure-in-production, SameSite cookies.
- Authentication endpoints share Redis-backed rate-limit storage across API replicas: registration and login allow five requests per minute per client IP, and password-reset requests allow three per minute. Set `TRUST_PROXY_HOPS` to the exact number of trusted reverse proxies in production so Express derives client IPs correctly; it defaults to zero in development. Keep Redis private; apply edge limits and monitor throttling before exposing the API publicly.
- Verification-link resend uses a generic response for unknown, active, and pending accounts; it is rate limited and atomically invalidates prior unused links before issuing a replacement.
- Derive tenant scope and role from the session. Test cross-tenant IDs for every data path. Use PostgreSQL RLS and composite tenant foreign keys in addition to scoped service methods.
- In Docker Compose, run migrations using the database owner, the API as `repus_api` (`NOBYPASSRLS`), and only trusted queue workers as `repus_worker` (`BYPASSRLS`). Runtime grants are installed as default privileges for migration-created objects. A non-owner role is subject to RLS only on tables where policies are enabled; audit every table and query before production and rotate the local example credentials.
- Authentication bootstrap uses transaction-local email, session-token-hash, and one-time-token-hash claims to resolve the tenant before installing the normal tenant claim. Keep these lookups inside the database helpers; do not query authentication tables from a new API path without a scoped helper.
- Member access revocation disables that workspace membership, deletes its workspace sessions, invalidates its unused invitation tokens, revokes keys created by that member in that workspace, and writes an audit event. The account and its other workspace memberships remain intact. Role edits, removal, invitation resend, and restoration conditionally match the role/status used for authorization; a concurrent promotion or membership change returns a conflict and rolls back any token changes. Invitation resend explicitly scopes token invalidation to the selected workspace even when token lookup requires the account's home-tenant context. Restoration is limited by the role hierarchy and creates no session or API key; a restored member must authenticate again and create new keys if needed.
- Never log secrets, passwords, raw auth tokens, or unnecessary subscriber PII. Use hashes for session and one-time-token lookup. Account email outbox rows hold encrypted capabilities under tenant RLS for worker delivery. Redis jobs carry token IDs. The worker checks decrypted values against their lookup hashes and clears encrypted payloads after provider acceptance, terminal failure, expiry, or use. An interrupted submission retains its delivery status so a signed provider event can reconcile it after the payload is cleared. Development logs omit recipient addresses and capability URLs. Local verification, reset, and invitation links are returned only to the requesting browser in development.
- Consume email-verification and password-reset tokens with a conditional single-row update (`usedAt IS NULL` and unexpired) in the same transaction as the account change. A pre-transaction token read is only a lookup; it must not authorize a second concurrent use.
- API keys are random bearer secrets stored only as SHA-256 hashes, shown once at creation, scoped to a tenant and a MARKETER/VIEWER role, and checked for expiry/revocation under an RLS hash capability. Do not include key values in logs or analytics.
- Platform administration is limited to active users whose normalized email is listed in `PLATFORM_ADMIN_EMAILS`; API keys never inherit platform-admin privileges. Cross-tenant quota changes execute inside an explicit transaction-local `app.platform_admin` claim, and tenant controls are recorded in a platform audit log. Keep this allowlist restricted and rotate access through the deployment secret store.
- SES event messages are processed only from the configured SQS queue and exact `AWS_SES_SNS_TOPIC_ARN`. SNS signatures are verified against HTTPS certificates from the configured AWS region before parsing the event; arbitrary certificate URLs and subscription auto-confirmation are rejected. Keep the SQS queue private, restrict its resource policy to the SNS topic, disable raw message delivery, and configure a redrive DLQ for invalid or repeatedly failing messages.
- Require documented marketing permission and source for campaign eligibility. Suppress unsubscribe, complaint, and hard-bounce addresses immediately; never silently reactivate on re-import.
- Token-bearing unsubscribe and subscription-confirmation pages, plus click redirects, must be non-cacheable, set `Referrer-Policy: no-referrer`, and disable MIME sniffing so capability URLs are not retained or forwarded to destination sites.
- Account verification and password-reset pages and API responses are non-cacheable, use `Referrer-Policy: no-referrer`, and disable MIME sniffing. Apply these headers before token validation so error responses have the same protections; authenticated session endpoints also use no-store response headers.
- Treat marketing permission as specific to the normalized email address. Contact email changes must include explicit fresh-permission attestation, collection source, and non-future collection date; reject suppressed destinations, suppress queued sends to the old address, and release their reservations. Interrupt in-flight sends and verify the recipient snapshot still matches the contact at the worker's provider boundary. When double opt-in is enabled, require confirmation at the new address and invalidate earlier unused confirmation links.
- Double opt-in is an optional workspace setting. Pending contacts are excluded from campaign audiences until a one-time, 48-hour confirmation capability is POSTed; GET-only link scanners do not subscribe them. Store only a token hash for validation and an encrypted copy for durable email queue recovery.
- Unsubscribed contacts can be reactivated only through the audited, explicit fresh-permission flow with source/date evidence. Imports never reactivate them. Clear only an unsubscribe suppression after the fresh evidence (and, when enabled, the confirmation POST); never clear hard-bounce or complaint suppressions through this path, and retain timestamped unsubscribe history across subsequent opt-outs.
- Bulk unsubscribe writes permanent unsubscribe/suppression records. Contact deletion removes the profile from lists and future sends, redacts profile fields, and retains recipient/event snapshots for campaign reporting; document and enforce a production retention policy for those historical snapshots.
- Sanitize authored email HTML with a narrow inline-style allowlist for email layout, escape personalization values, validate uploaded CSV content, and constrain tracked redirects to campaign links. Do not broaden the CSS allowlist without security review.
- Keep campaign image objects private; validate PNG/JPEG/WebP magic bytes and serve them only through unguessable, hashed database capabilities with a fixed content type and `nosniff`.
- Enforce per-workspace image storage under a tenant advisory lock and show current usage in the campaign editor. Do not expose storage object keys or image capability tokens in logs.
- Serialize image deletion with campaign/template content writes and refuse deletion while saved content references the capability URL.
- Restrict global sending controls to allowlisted platform administrators; background workers can read the pause flag but cannot change it.
- Public abuse reports accept bounded sender/message details without authentication, are throttled to five submissions per hour per API rate-limit bucket, and use a transaction-local insert-only RLS capability. Anonymous requests cannot read or edit reports; platform admins can review and change status with audited updates. Rate limits use shared Redis storage across API replicas; keep Redis private and use a dedicated production instance or managed Redis service.
- Verify SES/SNS authenticity before processing events; store provider event IDs durably for idempotency.
- Store secrets in environment/managed secret stores. Use production IAM roles instead of static AWS keys. Encrypt backups and private uploads.
- Compose runtime containers receive service-specific environment variables; never pass the owner `DATABASE_URL`, API/worker database passwords, or AWS secrets into the web container. The migration service alone receives the database-owner URL.
- Follow applicable privacy and email marketing laws for each audience. Provide sender identity, working unsubscribe, acceptable-use policy, abuse contact, and data retention/deletion processes.

Before a public launch, complete independent security review, rate-limit testing, backup restore exercise, abuse response runbook, and infrastructure hardening.
